# 개발 에이전트 공통 규칙

## 문서 읽기와 역할

1. 이 파일과 [Tasks.md](Tasks.md)의 재개 기록을 먼저 읽는다.
2. 필요한 기능의 정책은 [PRD.md](PRD.md), 화면은 [Design.md](Design.md)와 [design-mockup](../design-mockup/index.html), 기술/경로는 [Architecture.md](Architecture.md)를 읽는다.
3. 완료·미완료 상태는 Tasks에만 기록한다. 이전 문서/구현의 완료 기록을 그대로 새 구현에 적용하지 않는다.
4. 다섯 MD와 목업 폴더가 기준이다. 별도 로드맵·단계 계획·중복 규칙 문서를 계속 늘리지 않는다. 새 결정은 담당 문서 한곳에 쓰고 다른 곳은 링크한다.
5. 최신 사용자 요청 > 이 통합 문서 > 보존 목업의 오래된 문구 순으로 적용한다. 충돌은 숨기지 말고 설명한다.

이 문서는 코드·설계·개발 환경을 실제로 변경하는 작업에서 참고한다. 단순 질의나 설명 요청에는 불필요하게 검토하지 않는다. 사용자와 에이전트의 상시 역할 및 문서 선택 원칙은 루트의 [AGENTS.md](../AGENTS.md)에 둔다. 상세 개발 규칙은 이 파일에서 관리해 두 문서의 규칙을 중복하지 않는다.

## 협업과 코드 작성
- 실행한 명령어가 있다면 꼭 알려준다
- vite, npm, git등 개발자가 ide 내의 터미널을 활용할 수 있다면 할수있게 알려준다
- 개발 서버 실행·종료와 터미널 명령은 사용자가 직접 제어하는 것을 우선한다. 서버가 필요하면 실행 명령과 확인 주소를 안내하고, 사용자가 요청하지 않은 백그라운드 실행·종료는 하지 않는다.
- 터미널 명령은 되도록 사용자가 한다.
- 화면 하나와 해당 기능/이동을 완성한 뒤 다음으로 간다. 파일/컴포넌트/API를 미리 전부 만들지 않는다.
- 새 테이블·DB 함수·트리거·공유 스키마 변경, 별도 서버·Edge Function 추가는 필요/대안/영향을 설명하고 사용자 검토 후 진행한다.
- 일반 기능은 React/TypeScript + supabase-js CRUD로 처리한다. 과도한 RPC·프로시저·제약·추상화는 피한다.
- 실제 필요한 위치에만 파일을 만들고 경로 지도를 갱신한다. 테스트만을 위한 불필요한 소스는 만들지 않는다.
- 소스는 `src/features/<feature>/`에 기능별로 둔다. 화면 이름은 기능 접두어를 붙여 명확히 하고(예: `AuthIdPage.tsx`), 화면 전용 하위 컴포넌트·훅·스타일은 그 화면 폴더에 둔다.
- 화면 컴포넌트는 JSX 렌더링과 자식 전달에 집중하고, 상태·요청 호출·이벤트 흐름은 화면 전용 `use<Feature>Page.ts` 훅으로 분리한다. 실제 API 요청은 여러 화면이 쓸 수 있도록 기능 루트의 `<feature>.api.ts`에 둔다.
- 기존 프로젝트의 CSS 방식을 유지하고 화면 전용 CSS는 해당 화면 폴더에 둔다. 화면 사이에서 실제 공유하지 않는 타입·상수·barrel 파일은 만들지 않는다. 공유 타입은 별도 타입 파일로 둔다.
- 바텀시트의 닫힘은 공통 규칙이다. `src/lib/useBottomSheetClose.ts`와 `bottom-sheet.css`의 320ms ease-in-out 닫기를 재사용하고, ×·배경·저장 성공 등 모든 정상 닫기 경로에 적용한다. 닫기 전환이 끝나기 전에 시트를 제거하거나 화면을 이동하지 않는다. 저장 중에는 사용자 닫기를 막는다. 중앙 확인 팝업은 바텀시트와 구분한다.
- 승인된 디자인을 기준으로 한다. 검토가 필요하면 구체적인 선택지와 추천을 바로 제시하며 이미 승인한 부분을 다시 묻지 않는다.
- 변경한 화면·함수·파일과 사용자가 확인할 동작을 결과에 알린다. 실행하지 않은 테스트/원격 작업을 완료라고 하지 않는다.
- 터미널을 실행하거나 검토받을경우 실행이유와 결과를 먼저 설명해준다.

## 비용과 검증

- 요청한 화면의 정상 흐름과 관련 실패 하나 정도를 짧게 확인한다. 사소한 변경마다 전체 lint/테스트/빌드를 반복하지 않는다.
- 검증을 위해 임시 테스트 파일을 만들었다면 검증이 끝난 뒤 해당 파일을 삭제한다. 검증 명령과 결과는 Tasks 재개 기록에 남기며, 완료된 테스트 파일은 프로젝트에 보관하지 않는다.
- 대규모 테스트/RLS/보안 종합 검토는 Tasks의 MVP 완성 시점과 앱 출시 직전에 집중한다. 문서만 바꾸면 링크/내용 확인만 한다.
- 실패하거나 검증하지 않은 부분은 Tasks 재개 기록에 남긴다. 자동 테스트를 생략한 것을 성공으로 표현하지 않는다.
- 실제 확인된 토큰/사용량 잔여 한도가 5% 이하이면 안전한 지점에서 멈추고 현재 상태·변경 파일·마지막 확인·다음 행동을 Tasks에 저장한다. 알 수 없는 비율을 추측하지 않는다.
- MD는 수시 갱신하되 HTML은 별도 요청/합의된 종료 시점에만 갱신한다. 임의의 문서 자동생성·검증 파이프라인을 만들지 않는다.

## 기본 보호 규칙
- 기존 RLS/공유 권한을 임의로 해제하지 않는다. 막힌 기능만 필요한 최소 변경을 검토받는다.
- 2026-10-05 사용자 위임: 기존 승인 설계 범위의 일반 기능 구현과 필요한 최소 가계부 권한/정책 SQL은 재승인 없이 진행한다. 새로운 테이블·함수·트리거, 공유 프로젝트 영향, 삭제/데이터 손실이나 미확정 제품 정책은 검토 대상으로 남긴다. 검토가 필요한 부분은 Tasks에 기록하고 독립적으로 진행 가능한 다음 기능을 이어간다.
- 브라우저에는 URL/공개 publishable key만 사용한다. secret/service-role/사용자 토큰을 소스·화면·로그에 출력하지 않는다.
- 공유 auth.users/tb_user 및 yWeather 번호/함수는 보호한다. 승인 없이 새 사용자 테이블이나 동의 이력 테이블을 만들지 않는다.
- 로컬 파일 정리와 Supabase 원격 변경은 별개다. 함수 제거는 실제 정의/의존성 확인과 복구용 정의 보존 후 승인 범위만 처리하며 CASCADE 일괄 삭제는 쓰지 않는다.
- 실제 삭제·계정 탈퇴는 테스트 계정으로 확인한다. 데이터 손실 가능성이 있는 변경은 범위와 복구 가능 여부를 먼저 알린다.
- 사용자 변경/작업은 보존한다. 무관한 파일을 덮어쓰거나 요청 없이 Git 초기화/커밋/배포하지 않는다.
- 필요한 MCP/연결 도구가 있으면 그 기능 단계에서 이유를 설명한다. 개발 초기부터 도구·서버를 추가하지 않는다.

## 작업 종료 기록

Tasks의 재개 기록에 날짜, 마지막 완료 단계, 남은 일, 변경 파일, 원격 변경 여부, 최소 확인 결과, 다음 행동 한 가지를 남긴다. 이 기록이 다음 세션의 출발점이다.
