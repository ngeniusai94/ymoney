# YMoney 앱 개발·운영 가이드

- 작성일: 2026-11-15
- 적용 대상: React 웹 가계부 서비스와 이를 WebView로 제공하는 React Native 앱
- 우선 플랫폼: iOS / 배포 방식: 사용자가 Xcode에서 직접 빌드·배포

## 1. 목적과 기본 원칙

YMoney는 React 웹을 서비스의 중심으로 유지하면서 React Native 앱을 통해 App Store에 출시하고 운영한다.

1. 가계부 화면, 입력 검증, 수입·지출 처리, 통계, 서비스 상태와 API 연동은 웹이 담당한다. 데이터 접근 권한과 최종 검증은 서버에서 보장한다.
2. 앱은 WebView 컨테이너와 운영체제 기능 실행을 담당한다. 웹의 업무 로직을 앱에 중복 구현하지 않는다.
3. 웹에서 브릿지 함수를 호출하면 앱이 허용된 네이티브 기능을 실행하고 결과를 웹으로 반환한다.
4. 모든 앱 기능 호출에는 앱 환경 확인과 기능 지원 여부 확인을 둔다. 브릿지가 없는 일반 브라우저에서도 웹의 핵심 가계부 기능은 동작해야 한다.
5. 개발 담당 AI는 설계, 소스 작성, 적용 안내, 검증과 운영 대응을 담당한다. 사용자는 안내에 따라 소스를 붙여 넣고 Xcode에서 서명, 빌드, TestFlight 및 App Store 배포를 직접 수행한다.
6. 이 문서는 개발 전 참고 기준이다. 실제 구현과 다른 항목은 구현 완료로 간주하지 않으며, 변경 시 코드와 문서를 함께 갱신한다.

## 2. 확인된 현재 상태

- 사용자 지정 웹 저장소: https://github.com/ngeniusai94/ymoney
- 로컬 작업 공간에는 `app/` React Native 프로젝트가 있다. 웹 소스는 이번 로컬 확인 범위에 없으므로 웹의 내부 구조는 확정하지 않는다.
- `app/App.tsx`는 스플래시 표시 후 `https://ymoney.vercel.app/`을 WebView로 연다.
- `app/package.json`에는 React Native와 `react-native-webview`가 선언되어 있다. 버전 선언만으로 설치 상태나 Xcode 빌드 성공을 보장하지 않는다.
- 현재 `App.tsx`에는 WebView `onMessage`와 브릿지 요청·응답 처리가 없다.
- Xcode 작업 공간은 `app/ios/app.xcworkspace`이다.
- 아래 브릿지 API와 폴더 구조는 **향후 구현 기준**이다. 이 문서를 추가하는 것만으로 브릿지가 구현되지는 않는다.

## 3. 웹과 앱의 책임

| 영역 | 웹·서버 책임 | 앱 책임 |
| --- | --- | --- |
| 가계부 | 거래 CRUD, 분류, 예산, 통계, 서버 저장 | 업무 로직 구현 없이 웹 표시 |
| 화면 | 서비스 화면, 라우팅, 사용자 안내 | Safe Area, 키보드, 시스템 UI와 WebView 조정 |
| 공유·내보내기 | 공유 데이터와 내보내기 파일 생성 | iOS 공유 시트, 파일 저장 등 OS 처리 |
| 사진·카메라 | 영수증 입력 흐름, 업로드 및 서비스 처리 | 사용자가 요청한 미디어 선택·촬영과 권한 처리 |
| 알림 | 알림 목적, 사용자 설정과 서버 발송 정책 | 권한 요청, 토큰 취득, 알림 수신·탭 이벤트 |
| 인증 | 계정·세션·접근 권한 정책 | 필요한 경우 OS 로그인 UI, 안전한 자격 증명 저장 |
| 생체 인증 | 재인증을 요구할 업무 흐름 | OS 인증 결과 반환. 서버 인증을 대체하지 않음 |
| 장애 | API 오류, 업무 실패 안내 | 웹 로드 실패, 오프라인 복구, 앱 충돌 대응 |

앱은 웹의 요청 없이도 초기화, 화면 복귀, 딥링크, 알림 탭 등 OS 이벤트를 처리할 수 있다. 이때도 서비스 판단은 웹·서버에 맡기고, 브릿지가 준비되면 필요한 이벤트만 전달한다.

## 4. 권장 코드 구성

기존 구조가 있다면 이를 우선하고 다음 책임을 분리한다. 처음부터 모든 파일을 만들 필요는 없다.

```text
웹 저장소/
  src/native/bridge.ts        # 환경 판별, 준비 상태, 요청·응답, 타임아웃
  src/native/types.ts         # 프로토콜과 기능별 타입
  src/native/features.ts      # 앱/웹 분기와 브라우저 대체 동작

app/
  App.tsx                    # WebView 구성과 앱 생명주기
  src/bridge/                 # 검증, 명령 라우팅, 응답 전송
  src/native/                 # 공유·권한 등 기능별 네이티브 실행
  docs/APP_DEVELOPMENT_GUIDE.md
```

화면마다 직접 `postMessage`를 작성하지 않는다. 웹 공통 어댑터에 전송을 모으되, 기능 진입점에서 앱/웹 분기를 읽고 확인할 수 있게 한다.

## 5. 앱 환경 판단과 일반 웹 대응

### 필수 구분

- **브릿지 전송 가능 여부**: `typeof window !== 'undefined'`와 `window.ReactNativeWebView?.postMessage` 함수 존재 여부를 확인한다. SSR에서도 안전해야 한다.
- **브릿지 준비 상태**: 웹이 핸드셰이크를 완료하고 응답 리스너가 준비되었는지 확인한다.
- **기능 지원 여부**: 앱이 반환한 `capabilities`에서 필요한 명령을 확인한다. 앱이라는 이유만으로 모든 기능이 지원된다고 가정하지 않는다.
- User-Agent나 URL의 `isApp=true`만으로 기능을 호출하지 않는다. 환경 판별은 화면 분기를 위한 정보이며 인증·권한 증명이 아니다.
- 초기 준비 중에는 잠시 비활성화하거나 준비 완료를 기다린다. 준비 지연을 브라우저로 잘못 판정하지 않도록 `initializing / ready / unavailable` 상태를 구분한다.

### 기능 진입점 예시

아래는 **향후 웹 어댑터 구현 후 적용할 사용 형태**이다. `bridge`와 `shareInBrowser`는 아직 존재하는 코드가 아니며, 이 예시만 붙여 넣어 실행할 수는 없다. 실제 기능을 개발할 때는 어댑터와 대체 동작까지 완전한 소스로 제공한다.

```ts
async function shareReport(title: string, url: string) {
  // 앱의 초기 핸드셰이크를 제한된 시간 동안 기다린다.
  await bridge.waitUntilSettled();

  if (bridge.isNativeApp() && bridge.isReady()
      && bridge.supports('share.open')) {
    return bridge.request('share.open', { title, url });
  }

  // 일반 브라우저 또는 해당 기능이 없는 구버전 앱의 대체 처리.
  return shareInBrowser({ title, url });
}
```

브라우저 대체 처리도 실행 가능 여부와 사용자 제스처 요구를 확인한다. 예를 들어 Web Share API가 없으면 링크 복사나 링크 표시를 제공한다. 준비 대기 때문에 사용자 제스처가 만료될 수 있는 API는 준비 완료 후 사용자가 다시 누르게 한다.

| 앱 기능 | 일반 브라우저·미지원 앱에서의 처리 |
| --- | --- |
| 공유 | Web Share API, 미지원 시 링크 복사 또는 표시 |
| 파일 내보내기 | 브라우저 다운로드, 미지원 시 파일 링크 제공 |
| 사진 선택 | 웹 파일 입력 사용, 촬영 지원은 브라우저별 확인 |
| 푸시 알림 | 지원 환경에서만 웹 알림 제공, 그 외 앱 설치 안내나 기능 숨김 |
| 생체 인증 | 별도 웹 인증 수단 또는 재로그인 제공. 인증 자체를 생략하지 않음 |
| 앱 설정 열기 | 브라우저에서는 지원 안내 제공 |

취소, 권한 거부, 타임아웃을 모두 웹 대체 실행으로 연결하지 않는다. 실행 여부가 불확실한 요청을 다시 수행하면 공유 창이나 저장이 중복될 수 있다.

## 6. 브릿지 통신 규약

### 전송과 메시지

- 웹 → 앱: `window.ReactNativeWebView.postMessage(JSON.stringify(message))`.
- 앱: WebView `onMessage`에서 JSON을 파싱하고 검증한 뒤 허용된 핸들러로 전달한다.
- 앱 → 웹: `injectJavaScript` 등을 사용해 웹 어댑터의 고정 수신 함수에 직렬화된 메시지를 전달한다. 명령 인자에서 실행 코드를 조립하지 않는다.
- WebView 공식 문서에 따르면 `onMessage` 설정이 있어야 웹의 `postMessage`가 주입되며 전송 인자는 문자열이어야 한다.

요청 예시:

```json
{
  "version": 1,
  "kind": "request",
  "id": "session-uuid:request-uuid",
  "method": "share.open",
  "params": { "title": "가계부 요약", "url": "https://ymoney.vercel.app/" }
}
```

성공 및 실패 응답 예시:

```json
{ "version": 1, "kind": "response", "id": "session-uuid:request-uuid", "ok": true, "result": { "status": "completed" } }
```

```json
{ "version": 1, "kind": "response", "id": "session-uuid:request-uuid", "ok": false, "error": { "code": "PERMISSION_DENIED", "message": "권한이 필요합니다." } }
```

### 준비·수명주기·호환성

1. 웹이 수신 함수를 먼저 등록한 뒤 `bridge.hello`를 요청한다. 브릿지 주입이 늦으면 횟수와 시간을 제한해 재시도한다.
2. 앱은 프로토콜 버전, 앱 버전·빌드, 플랫폼, 지원 명령 목록인 `capabilities`를 반환한다. `bridge.hello` 자체는 지원 기능 조회 전 호출 가능한 기본 명령이다.
3. 호환되는 응답을 받은 웹만 준비 완료로 전환한다. 실패하면 핵심 웹 기능을 유지하고 앱 전용 기능에는 대체 동작 또는 안내를 제공한다.
4. 요청마다 고유 ID와 타임아웃을 둔다. 기본 제안은 15초이며 촬영·사용자 입력 등은 별도 정책을 정한다. 타임아웃은 OS 작업의 취소나 미실행을 뜻하지 않는다.
5. 알림 탭처럼 요청과 무관한 메시지는 `kind: "event"`와 이벤트 이름을 사용한다. 중요한 이벤트는 준비 전 제한된 큐에 보관하고 전달 확인·중복 제거 정책을 둔다.
6. 새로고침, 새 문서 이동, WebView 재생성 시 세션과 준비 상태를 초기화한다. 이전 요청을 정리하고 이전 문서의 응답이 새 문서로 전달되지 않게 한다.
7. 알 수 없는 메서드·버전은 오류로 응답한다. 구버전 앱에 새 웹을 배포해도 기존 규약을 유지한다. 기능 제거·강제 업데이트는 별도 전환 계획으로 진행한다.

공통 오류 코드는 `UNSUPPORTED_METHOD`, `UNSUPPORTED_VERSION`, `INVALID_PARAMS`, `NOT_READY`, `PERMISSION_DENIED`, `CANCELLED`, `TIMEOUT`, `INTERNAL_ERROR`를 기준으로 한다. OS API가 구별할 수 없는 결과를 임의로 성공·취소로 확정하지 않는다.

## 7. 브릿지와 데이터 보안

- 운영 WebView는 승인된 HTTPS origin만 내부에 표시한다. URL 파서로 scheme·host·port를 정확히 비교하고 문자열 접두사 검사는 사용하지 않는다.
- 외부 링크, 새 창, 리디렉션, 딥링크를 별도로 검사한다. 외부 페이지는 원칙적으로 시스템 브라우저로 보내며 브릿지 실행 권한을 부여하지 않는다.
- `originWhitelist`만으로 통신 보안이 완성되지는 않는다. 최상위 문서와 메시지 출처를 확인하고, iframe에서 특권 명령을 호출하지 못하도록 실제 iOS 동작까지 검증한다.
- 허용된 명령 목록과 명령별 파라미터 스키마, 길이·크기 제한을 적용한다. URL, 파일 경로, MIME 타입 등도 검증한다.
- 임의 JavaScript, 셸 명령, 임의 파일 접근, 전달받은 함수명 실행 기능을 만들지 않는다.
- 네이티브 기능 요청에도 로그인 상태와 사용자 의도 등 필요한 검사를 둔다. 앱 환경 판단을 서버 권한 검사로 사용하지 않는다.
- 가계부 데이터, 비밀번호, 인증 토큰, 영수증 원문을 로그에 남기지 않는다. 서버 비밀 키와 인증서 비밀은 웹·앱 소스 및 안내 문서에 넣지 않는다.
- 자격 증명을 네이티브에 저장해야 할 경우 Keychain 등 목적에 맞는 보안 저장소를 사용한다. 웹과 앱에 토큰을 무조건 복제하지 않는다.
- 신뢰하는 웹의 XSS도 브릿지 권한으로 이어질 수 있다. 웹 입력 처리, CSP 및 의존성 관리와 함께 검토한다.

## 8. 기능 개발 시 반드시 제공할 안내

개발 담당 AI는 사용자가 소스를 그대로 적용할 수 있도록 다음을 제공한다.

1. 기능의 목적, 웹·앱·서버의 변경 범위와 지원 환경.
2. 파일별 정확한 경로와 신규 생성/전체 교체/부분 수정 구분. 부분 수정은 찾을 원문과 교체 범위를 명시한다.
3. 실제 적용 코드에는 필요한 import, 타입, 오류 처리, 앱 판단 분기, 일반 웹 대체 처리까지 포함한다. 생략 부호나 미구현 함수를 실행 코드로 전달하지 않는다.
4. 새 패키지와 설치 위치, 명령 실행 디렉터리, 네이티브 의존성 변경 시 CocoaPods 처리 및 Xcode 설정.
5. `Info.plist`, Signing & Capabilities, entitlements, Privacy Manifest 등 필요한 변경과 목적. 사용하지 않는 권한을 추가하지 않는다.
6. 브릿지 명령·입출력·오류·지원 버전과 구버전 앱 동작.
7. 일반 브라우저, iOS 시뮬레이터, 실제 iPhone의 검증 방법과 기대 결과. 실행하지 못한 검증은 명확히 표시한다.
8. 웹만 배포하면 되는지, 새 앱 빌드·심사가 필요한지, 배포 순서와 문제 발생 시 복구 방법.

기존 사용자의 수정 사항을 먼저 확인하고 보존한다. 실제 파일 수정이 허용된 작업에서는 코드를 적용한 뒤 변경 내용을 안내할 수 있지만, 이번 합의의 기본 운영 방식은 사용자가 안내에 따라 직접 적용하고 Xcode에서 배포하는 것이다.

## 9. Xcode 빌드·배포 기본 절차

각 출시에서는 실제 설치 버전과 Apple의 최신 요구사항을 다시 확인한다. 아래는 공통 순서이며, 변경별로 구체적인 명령과 설정을 별도 안내한다.

1. 현재 소스·설정과 마지막 정상 버전을 백업하고 변경 목록을 기록한다.
2. 웹·앱 코드를 안내된 경로에 적용한다. 의존성 설치는 기존 lockfile과 패키지 관리 도구를 유지한다.
3. 네이티브 의존성 변경이 있으면 `app/`의 Ruby/Bundler 환경을 확인하고 `app/ios/`에서 `bundle exec pod install`을 실행한다. 필요한 최초 환경 설정은 따로 안내한다.
4. Xcode에서 `app/ios/app.xcworkspace`를 연다. Team, Bundle Identifier, 배포 대상 iOS, 권한 설정을 확인한다.
5. 실제 iPhone에서 Debug로 확인하고 Release 설정에서도 확인한다. 앱 포함 React Native JS 번들이 개발용 Metro 없이 실행되는지 확인한다.
6. 사용자에게 보이는 버전과 업로드용 빌드 번호를 정한다. 새 업로드에는 적절한 새 빌드 번호를 사용한다.
7. 실제 배포 대상을 선택해 Archive를 만들고 Organizer에서 검증·업로드한다. Xcode 버전에 따라 메뉴명이 달라질 수 있다.
8. TestFlight에서 웹 연결, 로그인 유지, 브릿지 기능, 권한 거부, 재실행을 확인한 뒤 App Store Connect의 정보와 심사 자료를 준비한다.
9. 사용자 본인이 제출·출시를 수행한다. 출시 후 충돌, 웹 로드 실패, 브릿지 오류와 API 장애를 관찰한다.

웹 변경도 출시된 모든 앱에 영향을 준다. 새 앱 기능은 지원 앱이 보급되기 전까지 기능 탐지로 보호한다. 네이티브 바이너리 변경은 새 앱 배포가 필요하며, 웹 업데이트로 심사 대상 기능 변경을 우회하지 않는다.

## 10. 검증·장애 대응 기준

- 일반 Safari/Chrome: 브릿지 없이 초기 로드, 거래 입력·조회, 기능별 대체 동작.
- 지원 앱: 핸드셰이크, 요청·응답 매칭, 연속 클릭, 취소, 권한 거부, 타임아웃.
- 구버전 앱: 신규 기능 미지원 상태에서도 핵심 웹 기능 유지.
- 앱 생명주기: 백그라운드 복귀, 종료 후 재실행, 새로고침, 세션 만료.
- 네트워크 장애: 오프라인, 웹 서버 오류, 느린 로딩에서 오류 화면과 재시도. 스플래시 종료를 웹 로드 성공으로 간주하지 않는다.
- 보안: 외부 페이지·iframe·잘못된 메시지·허용되지 않은 URL의 특권 호출 차단.
- 사용성: Safe Area, 키보드, 확대 글자, 화면 회전 및 지원 기기에서 입력·스크롤 확인.
- 관측: 앱·웹·브릿지 버전, 비식별 요청 ID, 오류 코드로 문제를 추적하고 민감한 payload는 제외한다.
- 복구: 웹 이전 버전 재배포와 기능 비활성화를 준비한다. App Store의 설치된 바이너리는 즉시 되돌릴 수 없으므로 긴급 수정 앱 배포 계획도 둔다.

## 11. 출시 전 추가 검토 및 미정 사항

다음은 구현 완료 또는 채택 확정 사항이 아니라, 해당 기능을 개발·출시하기 전에 결정할 항목이다.

| 우선순위 | 항목 | 검토할 내용 |
| --- | --- | --- |
| 출시 전 | 앱의 실질적 가치 | 단순 웹 포장을 넘어 영수증 입력, 공유·내보내기 등 사용자에게 필요한 앱 경험 선정. 특정 기능 추가만으로 심사 통과를 보장하지 않음 |
| 출시 전 | 웹 저장소·배포 환경 | 웹 소스 위치, 운영·검증 URL, 배포 권한, 브릿지 공통 타입 관리 방식 |
| 출시 전 | 계정·개인정보 | 로그인 방식, 앱 내부 계정 삭제, 개인정보처리방침, 데이터 보관·삭제, App Privacy 응답 |
| 출시 전 | 인증 연동 | 쿠키 지속성, 로그아웃, 외부 로그인 제공자의 WebView 허용 여부, 필요한 시스템 인증 세션·딥링크 |
| 출시 전 | 지원 범위 | 최소 iOS, iPhone/iPad, Xcode·SDK, 실제 의존성 호환성 |
| 출시 전 | 권한·자산 | 필요한 권한과 목적 문구, Privacy Manifest, 앱 아이콘·스플래시 이미지의 사용 권리 |
| 기능 도입 시 | 유료화 | 디지털 기능·구독 결제에 대한 적용 지역과 최신 App Store 결제 규칙 검토 |
| 기능 도입 시 | 푸시·딥링크 | APNs 구성, 토큰 갱신, 로그아웃 시 연결 해제, 링크 검증, 중복 전달 방지 |
| 운영 전 | 데이터 보호 | 백업·복구, 오류 수집 도구, 고객 문의, 장애 대응 담당과 절차 |

현재 `ios/app/Info.plist`에는 빈 위치 권한 설명 문자열이 있다. 위치 기능이 필요한지 확인하고, 필요하면 실제 목적을 설명하고 불필요하면 권한 설정 제거를 검토한다. 현재 아이콘·스플래시 이미지의 사용 권리도 출시 전에 확인한다.

Apple 심사 지침은 웹사이트 재포장 이상의 사용성(4.2), 개인정보와 권한 안내(5.1.1), 계정 생성 서비스의 앱 내부 계정 삭제(5.1.1(v)) 등을 규정한다. 로그인·결제 같은 조건부 요구사항은 실제 기능과 배포 지역에 맞춰 출시 때 다시 확인한다.

## 13. Git 관리 범위

- 로컬 Git 저장소 루트는 `app/`이다. 작업 공간 기준 `app/docs/`는 저장소 안에서 `docs/`로 표시된다.
- Git 추적 대상은 `docs/` 아래 문서와 제외 규칙을 유지하는 루트 `.gitignore`로 제한한다.
- React Native 소스, iOS·Android 프로젝트, 의존성 및 로컬 `AGENTS.md`는 로컬에 보관하고 이 저장소에는 새로 올리지 않는다.
- 기존 추적 파일은 로컬 파일을 보존한 채 인덱스에서 제외한다. 전환 커밋에는 해당 파일이 삭제로 표시되며, 과거 커밋 이력의 소스는 자동 제거되지 않는다.
- 앱 소스가 Git으로 백업되지 않으므로 Xcode 작업 파일과 마지막 정상 빌드 소스는 별도 비공개 백업으로 보관한다.
- 문서는 `git add docs/`로 추가한다. 제외된 앱 소스를 `git add -f`로 강제 추가하지 않는다.
